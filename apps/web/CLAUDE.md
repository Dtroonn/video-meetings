# @video-meetings/web

Next.js 16 frontend (App Router, React 19, HeroUI v3 on Tailwind CSS 4). See the root `CLAUDE.md` for monorepo-wide commands and conventions.

## Commands (run in `apps/web`, or use `pnpm --filter @video-meetings/web <script>` from the root)

- `pnpm dev` — dev server with Turbopack on **3000** (the api runs on 3001).
- `pnpm build` / `pnpm start` — production build / serve.
- `pnpm lint` — ESLint (`eslint-config-next` core-web-vitals + TypeScript rules).
- `pnpm check-types` — `next typegen && tsc --noEmit` (typegen generates route types first).

## Structure

The code follows **Feature-Sliced Design** (FSD v2.1, see the `feature-sliced-design` skill). Next.js routing lives in `app/` at the app root; `src/` holds only FSD layers.

- `app/` — Next.js App Router, **routing only**. Every page lives under `app/[lang]/` (the locale, `en` or `ru`, is the first URL segment): `[lang]/layout.tsx` (root layout, imports the global CSS, sets `<html lang>`), one `[lang]/**/page.tsx` per route that just re-exports a page slice (e.g. `export { RegisterPage as default, metadata } from '@/_pages/register'`). Outside `[lang]`: `favicon.ico` and `api/**/route.ts` files that just re-export a handler from `@/_app/api-routes` (`api/auth/refresh/route.ts` → `POST`). No logic or UI here. The one exception is **route segment config** (`instant`, `maxDuration`, …): Next reads it statically from the route file's own source (an `export const` with a literal value), so it must be written in `page.tsx` / `layout.tsx` itself; exported from a page slice, or re-exported, it is silently ignored.
- `proxy.ts` — Next.js Proxy (formerly middleware), at the app root next to `app/`, outside the FSD layers: locale redirect, session refresh, the list of public pages (everything else requires a session), redirect to login, 500 page when the api fails, guest-only redirects (see **Auth** below).
- `src/_app/` — FSD **app** layer: `styles/globals.css`; `api-routes/` (Route Handler implementations: `refreshTokens` for `POST /api/auth/refresh`). Global providers go here when needed.
- `src/_pages/` — FSD **pages** layer, one slice per route: `home/` (the public landing page, texts from the `home` dictionary namespace: `ui/home-page.tsx` composes `HomeHeader` (locale switcher, login button), `HeroSection`, `StepsSection`, `ProtocolSection`, `CtaSection`, `HomeFooter`; `ui/guest-only.tsx` `GuestOnly` renders its children only for signed-out visitors, see **Cache Components** below), `login/`, `register/`, `server-error/` (the `/500` page: "Something went wrong" with a reload button). A slice has segments `ui/` (components), `model/` (schemas, state), `api/` (requests only it makes, here Server Functions) and an `index.ts` public API.
  - `login/` — log-in page (email, password): `ui/login-page.tsx` (async page reading `?from=` + `generateMetadata`), `ui/login-form.tsx` (client form), `model/login-form.ts` (`createLoginSchema()`, `LoginError`), `api/login.ts` (`'use server'` `login()` → `POST /auth/login`, sets the session cookies, redirects to `from`).
  - `register/` — sign-up page (email, password, confirm password), same shape: `ui/register-page.tsx`, `ui/register-form.tsx`, `model/register-form.ts` (`createRegisterSchema()`, `RegisterError`), `api/register.ts` (`'use server'` `register()` → `POST /auth/register`; a 409 returns `emailTaken`, which the form shows on the email field).
- `src/shared/` — FSD **shared** layer, segments only, each with its own `index.ts`:
  - `api/` — `apiPost<T>()`: server-side JSON `POST` straight to `API_URL`, returning `{ ok: true, data }` or `{ ok: false, error: ApiErrorResponse }` (`status: 0` when the api is unreachable).
  - `auth/` — session plumbing: cookie names and `setSessionCookies` / `clearSessionCookies`, `getTokenExpiry` / `expiresWithin` (read a JWT's `exp` with `jose`'s `decodeJwt`, no signature check: the api verifies tokens), `rotateTokens` (refresh with a grace window), `safeRedirectPath` / `REDIRECT_PARAM`. Server Components only, from `@/shared/auth/server` (kept apart so `next/headers` stays out of `proxy.ts`): `isSignedIn()` — whether the request has a valid access token, wrapped in `React.cache` so all components of one render share one cookie read and token decode (per request, never across requests).
  - `config/` — `API_URL` (`process.env.API_URL`, default `http://localhost:3001`), also used by `next.config.ts`.
  - `i18n/` — locales (`en`, `ru`), **two public entries**:
    - `@/shared/i18n` — safe anywhere, `proxy.ts` included: `LOCALES`, `isLocale`, `splitLocale` (`/ru/login` → `{ locale: 'ru', path: '/login' }`), `localePath` (`('ru', '/login')` → `/ru/login`), `negotiateLocale` (cookie → `Accept-Language` → `en`), `LocaleSwitcher` (client: links to the same page in every locale, keeping the query).
    - `@/shared/i18n/server` — Server Components only: `getLocale()` (the `[lang]` segment via `next/root-params`) and `getDictionary()`. Kept apart because `next/root-params` fails to compile outside the App Directory: importing it through the main index broke `proxy.ts`.
    - **Dictionaries** are JSON, one file per locale: `dictionaries/en.json`, `ru.json`, namespaced by page (`home`, `login`, `register`, `serverError`) plus `common`. `en.json` defines the `Dictionary` type (also exported, type-only, from `@/shared/i18n` for Client Components' props) and every other locale is type-checked against it, so a missing key fails `check-types`. They're loaded lazily on the server; **Client Components never load them**: their Server Component parent passes only the strings they need as props (e.g. `LocaleSwitcher`'s `label`). If a deep client tree ever needs many strings, add a provider + context then, not before. No i18n library.
    - `formatMessage(template, values)` fills `{name}` placeholders (`"At most {max} characters"`), e.g. for limits from `@video-meetings/contracts`.
    - **Server Functions return codes, not texts:** they can't read `next/root-params`, so `login()` / `register()` return `{ code }` (typed as `keyof <page>.form.errors`, so the dictionary must have a message for every code) and the client form looks the message up in the strings its page passed it.
    - **Valibot schemas are factories** that take the form's `validation` messages: `createLoginSchema(messages)`. The client form builds it in `useMemo` with its dictionary strings; Server Functions don't use it.
  - `ui/` — `PasswordInput` (password input with a show/hide toggle, for use inside a `TextField`; the toggle's translated `labels` come from `common.passwordInput`), `ButtonSkeleton` (a `<Suspense>` placeholder exactly the size of a HeroUI button: same `buttonVariants` size, width reserved by the invisible `label`).
- `public/` — static assets served from `/`.
- Import alias: `@/*` → `src/*` (`@/_pages/register`, `@/shared/api`, `@/_app/api-routes`).

## Things to know

- **FSD rules:**
  - Layers import only from layers below: `_app` → `_pages` → (`features` → `entities` →) `shared`. Slices on the same layer never import each other.
  - Import a slice only through its `index.ts` (`@/_pages/register`, not `@/_pages/register/ui/...`). Inside a slice, use relative imports.
  - **Pages first:** put new code in the page slice that uses it. Move it down to `features/` / `entities/` only when several pages use it right now; generic, business-free code (UI helpers, api client) goes to `shared/`. Those layers don't exist yet; create them when the first such case appears, not ahead of time.
  - The `_app` / `_pages` underscores avoid a clash with Next's own `app/` / `pages/` folders. Don't recreate `src/app` or `src/pages`: Next would treat them as router folders.
  - Name files after their domain (`register-form.ts`), not their role (`types.ts`, `utils.ts`).
- **Moving the router folder** (e.g. `src/app` ↔ `app`) needs a `next dev` restart; Next picks the folder at startup.
- **Next.js 16 differs from older versions.** Before using a Next.js API, check the bundled docs in `node_modules/next/dist/docs/` (see `AGENTS.md` above). Don't rely on memory of Next 13–15 behaviour.
- **Cache Components are on** (`cacheComponents: true` in `next.config.ts`): each route is prerendered into a static shell, and runtime data must not block it.
  - Read request data (`cookies()`, `headers()`, `searchParams`, `isSignedIn()`) and `useSearchParams()` only **inside `<Suspense>`**, as low in the tree as possible, so the rest of the page stays static. On the home page only the guest-only parts are dynamic: each is wrapped in `<Suspense><GuestOnly>…</GuestOnly></Suspense>`.
  - **Fallbacks must have the final size (no layout shift):** reuse the real component's size classes (`ButtonSkeleton`, `LocaleSwitcherSkeleton`), or render the same markup with `invisible` content over a `Skeleton` (`CtaSection`). Fixed sizes like `h-9` would drift: HeroUI's `sm` buttons are 36px on touch and 32px on mouse devices. The fallback matches the signed-out version, so for signed-in visitors the guest-only parts still collapse once they resolve.
  - `app/[lang]/layout.tsx` lists every locale in `generateStaticParams` (required: the `[lang]` root param must have values to prerender), so `getLocale()` / `getDictionary()` work in the shell.
  - No clock or randomness in the shell (`new Date()`, `Math.random()`): it's a build error. Put it in a `'use cache'` function with `cacheLife` (the footer's `CurrentYear`) or behind `<Suspense>` + `connection()`.
  - `export const instant = false` (in the route file, see above) lets a page block on runtime data instead of producing a static shell. It does **not** force the page dynamic (reading runtime data already does that) and doesn't excuse clock/randomness errors. `app/[lang]/login/page.tsx` uses it, since the page reads `searchParams` (`?from=`) outside `<Suspense>`. Register does the same without it, so it still shows the "runtime data during prerendering" error in dev.
- **Server Components by default.** Add `'use client'` only to components that need state, effects, or browser APIs, and keep them as small leaves.
- **UI kit is HeroUI v3** (`@heroui/react` + `@heroui/styles`, built on React Aria); icons come from `@gravity-ui/icons`, the set HeroUI's docs use (decorative icons get `aria-hidden`, icon-only buttons an `aria-label`). v3 is not v2: no `HeroUIProvider`, no `framer-motion`, compound components (`<Card><Card.Header>…`), `onPress` instead of `onClick`. Check the v3 docs (or the `heroui-react` skill) before using a component; don't rely on v2 knowledge. Components ship with `'use client'`, so Server Components can render them directly.
- **Styling** is Tailwind CSS 4 (required by HeroUI v3) via `@tailwindcss/postcss`. `src/_app/styles/globals.css` imports `tailwindcss` and then `@heroui/styles` (the order matters), followed by theme variable overrides. There is no `tailwind.config.js`; colours, radii and dark mode come from HeroUI's theme variables. The light theme overrides a few of them for WCAG AA: darker `--accent` and `--danger` (HeroUI's white button text and red error text were ~3.6:1), a visible field border (`--field-border-width`, `--field-border`; HeroUI's fields are borderless and vanish on a white card), an accent border on focus (`--field-border-focus`) so it merges with the focus ring into one edge, a danger border on invalid fields (HeroUI only adds a red outline/ring, which left a grey or blue line inside it), and no divider on `InputGroup` prefix/suffix (it reuses the field border width, so it would otherwise appear). If you change them, keep white-on-accent, white-on-danger and danger-on-white at ≥ 4.5:1 including the hover state, and the field border at ≥ 3:1 against both the card and the page background. Use them via semantic utilities (`bg-background`, `text-foreground`, `accent`, …). Prefer HeroUI components and semantic variants over raw Tailwind colours (`zinc-*`, hex values). To customise the design, override HeroUI's theme variables in `globals.css` after the imports. Dark mode is switched with `class="dark"` / `data-theme="dark"` on `<html>`.
- **Talking to the api:** server code (Server Functions, Route Handlers, `proxy.ts`) calls the api directly at `API_URL` through `@/shared/api`; relative `/api` URLs don't work on the server. The browser calls same-origin `/api/...`, which `next.config.ts` rewrites to the api, so the api needs no CORS setup. Never hard-code `localhost:3001`. Rewrites are read at server start, so restart `next dev` after changing `API_URL`. Type api responses with `@video-meetings/contracts` (`AuthResponse`, `TokensResponse`, `ApiErrorResponse`, …).
- **Auth:**
  - **Tokens live in httpOnly cookies** (`access_token`, `refresh_token`; `SameSite=Lax`, `Secure` in production, `Max-Age` from each JWT's `exp`), so client-side JS never sees them. Cookies are cleared **only when the api answers 401** (the session is really over); on a network or server error they're kept, so the same session works again once the api recovers.
  - **Login and register are Server Functions** called from the client form inside `startTransition` (`isPending` drives the button). They don't re-validate the input: the api validates every request, and its errors come back as codes. They call the api, `setSessionCookies(await cookies(), …)` and `redirect()`. On failure they return an error object that the form shows via `setError`. Call `redirect()` outside any `try`: it throws.
  - **Locale in the URL:** `proxy.ts` first redirects any path without a locale prefix to the same path with one (`/login?from=x` → `/ru/login?from=x`): the `locale` cookie, else `Accept-Language`, else `en`. A request with a prefix stores it in the `locale` cookie (one year), so switching languages is remembered. Everything below works on the path **without** the prefix, and every redirect/rewrite it makes keeps the locale. Unknown paths (`/zz` → `/ru/zz`) are private, so a signed-out user lands on login, a signed-in one on a 404. Build in-app links with `localePath(locale, path)`.
  - **Protected by default:** `proxy.ts` has `PUBLIC_PATHS` (`/`, `/login`, `/register`, `/500`, locale-less); any other page sends a signed-out user to `/<locale>/login?from=<path>`. To make a new page public, add it to that set. On a public page a failed refresh never blocks rendering: a 401 just clears the cookies, a network/5xx error keeps them and the page renders as signed-out.
  - **Return path:** pages that require a session redirect to `/login?from=<path>`; login and register redirect to `from` afterwards and keep it in the link between the two pages. Always pass it through `safeRedirectPath()`, which only allows same-site paths (`//evil.com` → `/`), to prevent open redirects.
  - **Proactive refresh:** `proxy.ts` runs on every page and Server Function request, not on `/api/*` or static files: in production nginx sends `/api/*` straight to the api (the client adds the `Authorization` header itself), and the rest are our own Route Handlers, which handle the session themselves. If the access token is missing or expires within 30 s and a refresh token exists, it rotates the tokens. It writes the new pair to the response cookies, and also to the request cookies so Server Components and Server Functions in the same request already see it. `rotateTokens()` returns `{ ok: true, tokens }` or `{ ok: false, status }` with the api's status (`0` = unreachable), and the proxy acts on it:
    - **401** → clears the cookies; a private page redirects to `/login?from=<path + query>`, a public page renders without them (no redirect loop).
    - **Anything else** (0, 5xx) → keeps the cookies; a private page **rewrites** to `/500` with status 500. It's a rewrite, not a redirect, so the URL stays and reloading retries the original page. The App Router's built-in 500 page only renders for unhandled errors and can't be routed to, hence our own `app/[lang]/500` route.

    Signed-in users opening `/<locale>/login` or `/<locale>/register` are redirected to `/<locale>`.

  - **Grace window:** the api accepts each refresh token once, so parallel requests carrying the same old token would get 401s. `rotateTokens()` keeps a Map from old refresh token to the rotation's promise for 30 s; everyone presenting that token in the window gets the same new pair. Rejected tokens (4xx) are cached too; network and 5xx errors aren't, so the next request retries. The Map lives on `globalThis` (under a `Symbol.for` key), not in a module variable: `proxy.ts` and Route Handlers are bundled separately but run in one Node process, so they share it. This assumes **a single app instance**; several instances would need a shared store (e.g. Redis).
  - **`POST /api/auth/refresh`** is a Next Route Handler for client-side code: it rotates the cookies through the same grace window and returns 204; returns 401 and clears them when there's no refresh token or the api rejected it; returns 500 and keeps them when the api failed. It shadows the api's `/auth/refresh`, because filesystem routes match before `next.config` rewrites. The client doesn't call it yet; the ky client will call it on a 401 and retry.
- **Forms** use **react-hook-form** with **valibot** schemas (`@hookform/resolvers/valibot`). Wire HeroUI fields through `<Controller>`: `value`/`onChange`/`onBlur` go to `TextField`, `fieldState.invalid` to `isInvalid`, `field.ref` to `Input`, the message to `FieldError`. Set `validationBehavior="aria"` on `Form` so the schema, not native browser validation, decides what's invalid. Import limits (e.g. `PASSWORD_MIN_LENGTH`) and request types from `@video-meetings/contracts` instead of redefining them, so they stay in sync with the api. Cross-field checks (`v.partialCheck` + `v.forward`) only run once the fields they read are valid. For them to run at all while other fields have errors, set `criteriaMode: 'all'` in `useForm`: with the default `'firstError'` the resolver passes valibot `abortPipeEarly`, which skips the object-level check (an empty email hid "Passwords do not match"). Put `rules={{ deps: '<checked field>' }}` on the `Controller` of the other field the check reads (here `password` → `confirmPassword`), so the error appears or clears when either field changes.
- **Linting** comes from `@video-meetings/eslint-config/next`; **TypeScript** extends `@video-meetings/typescript-config/nextjs.json` (strict, bundler resolution).
- `AGENTS.md` and the `@AGENTS.md` import at the top of this file are managed by `next dev` — don't remove them.

## Checking UI changes

A UI change isn't done when lint and types pass; it must also be **checked visually** and **reviewed with the `ui-ux-pro-max` skill**.

- **Look at it in a browser** (the Playwright MCP server from the root `.mcp.json`) on the running dev server: take screenshots and read them, don't rely on the code alone. Cover every state the change touches (default, hover, keyboard focus, invalid, disabled, loading) at desktop (1280px) and mobile (375px) widths.
- **Review it with `ui-ux-pro-max`** against its rules, accessibility first: text contrast ≥ 4.5:1 and field/control boundaries ≥ 3:1 (measure computed colours, don't eyeball them), visible focus, labels and errors linked to their fields, heading order, touch target size, no horizontal scroll.
- Fix what the review finds, or report it if the fix is out of scope (e.g. a theme-wide change), then re-check.
