# @video-meetings/api

NestJS 12 backend. See the root `CLAUDE.md` for monorepo-wide commands and conventions.

## Commands (run in `apps/api`, or use `pnpm --filter @video-meetings/api <script>` from the root)

- `pnpm dev` — `nest start --watch`, listens on `PORT` or **3001** (3000 is the web app).
- `pnpm build` — type-checks, then compiles `src/` to `dist/` with SWC.
- `pnpm lint` — ESLint over `src/` and `test/` (type-aware rules).
- `pnpm check-types` — `tsc --noEmit`.
- `pnpm test` — unit tests (Vitest, `**/*.spec.ts`, config in `vitest.config.ts`).
- `pnpm test:e2e` — e2e tests (Vitest + supertest, `**/*.e2e-spec.ts`, config in `vitest.config.e2e.ts`).
- `pnpm db:migrate` — `prisma migrate dev`: create a migration from `prisma/schema.prisma` changes and apply it to the local DB (`--name <name>` to name it). It does **not** regenerate the client in Prisma 7 — run `pnpm db:generate` afterwards. `pnpm db:migrate:deploy` applies pending migrations only (CI/prod).
- `pnpm db:generate` — regenerate the Prisma client (also runs on `pnpm install` via `postinstall`). `pnpm db:studio` — Prisma Studio.
- Generate code with the Nest CLI: `pnpm exec nest g <schematic> <name>` (e.g. `module`, `controller`, `service`, `resource`).

## Structure

- `src/main.ts` — bootstrap (top-level `await`).
- `src/app.module.ts` — root module; register feature modules here. Also loads config (`ConfigModule`, validated by `src/config/env.validation.ts`), registers `CqrsModule.forRoot()` (global `CommandBus`/`QueryBus`) and the global `ValidationPipe`.
- `src/prisma/` — global `PrismaModule` exporting `PrismaService` (a `PrismaClient`); inject it wherever DB access is needed.
- `src/<module>/commands/<name>/`, `src/<module>/queries/<name>/` — one folder per use case holding `<name>.command.ts` / `<name>.query.ts` and its `<name>.handler.ts` (see **CQRS** below).
- `src/users/` — `CreateUserCommand`, `GetUserByIdQuery`, `GetUserCredentialsByEmailQuery`; `users.types.ts` (`PublicUser`, `UserCredentials`); `dto/user-response.dto.ts` (`UserResponseDto`). The module exports nothing.
- `src/auth/` — `POST /auth/register` and `/auth/login` (return `{ user, accessToken, refreshToken }`) and `/auth/refresh` (returns `{ accessToken, refreshToken }`), backed by `RegisterCommand`, `LoginCommand`, `RefreshTokensCommand`. `services/` holds `TokensService` (issue/verify/consume tokens) and `PasswordService` (argon2) used by the handlers; `guards/access-token.guard.ts` is the global `AccessTokenGuard`; `decorators/` holds `@Public()` and `@CurrentUser()`; `dto/` holds the request/response DTOs; `auth.types.ts` has internal types (`AuthTokens`, `AuthResult`, `AccessTokenPayload`, `AuthenticatedUser`).
- `src/meetings/` — `POST /meetings`, `GET /meetings` (own and invited meetings, earliest first), `GET /meetings/:id`, backed by `CreateMeetingCommand`, `GetMeetingsQuery`, `GetMeetingByIdQuery`. `meetings.types.ts` has `MeetingDetails` (a meeting plus participant user ids); `meetings.mapper.ts` holds the Prisma `include`/`where` pieces and the row → `MeetingDetails` mapping shared by the handlers.
- `prisma/schema.prisma`, `prisma/migrations/` — DB schema and migrations (committed). `prisma.config.ts` — Prisma CLI config.
- `src/generated/prisma/` — generated Prisma client; gitignored, and ignored by ESLint and Prettier. Import from `@/generated/prisma/client`.
- `src/**/*.spec.ts` — unit tests next to the code they test.
- `test/*.e2e-spec.ts` — end-to-end tests.

## Things to know

- **Database:** PostgreSQL from the root `compose.yaml` (`pnpm db:up` from the root), accessed through **Prisma 7** with the `prisma-client` generator and the `@prisma/adapter-pg` driver adapter. Prisma 7 no longer reads the URL from the schema: the CLI takes it from `prisma.config.ts`, the app passes it to the adapter in `PrismaService`. Tables and columns are snake_case via `@@map`/`@map`. After changing the schema run `pnpm db:migrate --name <name>` and commit the migration.
- **`prisma.config.ts` reads `process.env.DATABASE_URL`, not Prisma's `env()` helper**, because `env()` throws when the variable is unset and would break `prisma generate` on install in environments without a DB (CI).
- **Env variables** (`apps/api/.env`, template `.env.example`): `DATABASE_URL`, `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET`, `JWT_ACCESS_TTL` / `JWT_REFRESH_TTL` (seconds, default 900 / 604800). They're validated at startup; add new ones to `EnvironmentVariables` and read them with `ConfigService<EnvironmentVariables, true>`.
- **CQRS** (`@nestjs/cqrs`): controllers only build a command/query from the DTO and dispatch it through `CommandBus`/`QueryBus`; logic lives in handlers. Anything that writes is a command — including login and refresh, which store refresh tokens; reads are queries. Commands/queries extend `Command<TResult>` / `Query<TResult>` so `execute()` is typed without casts. Modules talk to each other only through the buses (auth dispatches users' commands/queries and imports `UsersModule` so their handlers are registered), never by injecting another module's services. Helpers shared by several handlers of one module (e.g. `TokensService`) stay plain injectable services. Register each handler in its module's `providers`.
- **Password hashes stay in the users module:** handlers return `PublicUser` (no `passwordHash`); only `GetUserCredentialsByEmailQuery` returns the hash, split off from the user so the user part can go to a client as is.
- **DTOs** live in `<module>/dto/`, one class per file. Everything a client sends or receives is a DTO class: `<Name>RequestDto` / `<Name>ResponseDto` named after the endpoint (`LoginRequestDto`, `LoginResponseDto` in `login-request.dto.ts` / `login-response.dto.ts`); response shapes shared by several endpoints get a generic name (`UserResponseDto`, `TokensResponseDto`, `AuthResponseDto`) and the endpoint DTOs extend them. Handlers return internal types (`AuthResult`, `PublicUser`), never DTOs; the controller maps them with the response DTO's constructor. Response DTOs copy fields one by one rather than spreading the input, so a new DB column can't reach clients by accident. Request/response shapes and their limits (`PASSWORD_MAX_LENGTH`, …) are defined in `@video-meetings/contracts`; DTO classes `implements` the matching interface and import the constants (dates are ISO strings there, so response DTOs call `toISOString()`). Types that never leave the server go in `<module>.types.ts`, without a `Dto` suffix.
- **Validation:** DTOs use `class-validator` / `class-transformer`; the global `ValidationPipe` has `whitelist`, `forbidNonWhitelisted` and `transform` on. It's provided via `APP_PIPE` in `AppModule`, not `app.useGlobalPipes()` in `main.ts`, because e2e tests build the app from `AppModule` and never run `main.ts`. DTO and injected classes must be value imports (not `import type`), or Nest loses the metadata it needs.
- **Auth:** passwords are hashed with **argon2** (argon2id). Emails are trimmed and lowercased by the DTOs. Access tokens are JWTs with payload `{ sub: userId, email }`; never put the password hash in them. Access and refresh tokens are signed with **different secrets**, so one can't be used as the other. Each refresh token has a row in `refresh_tokens` keyed by its `jti`; `/auth/refresh` deletes that row with a single conditional delete, so every refresh token works once (rotation) and concurrent reuse can't both succeed, while other sessions keep their own rows. Login with an unknown email still runs an argon2 verify against a dummy hash (`PasswordService.verify`), so response time doesn't reveal which emails are registered.
- **Every route requires an access token by default:** `AccessTokenGuard` is registered as `APP_GUARD` in `AuthModule`, so a new endpoint can't be left open by accident. It reads `Authorization: Bearer <accessToken>`, verifies it with `TokensService.verifyAccessToken` (signature and expiry only, no DB lookup — access tokens are short-lived) and sets `request.user`. Mark open routes/controllers with `@Public()` (auth endpoints and `GET /` are); read the user in controllers with `@CurrentUser() user: AuthenticatedUser`. Other modules may import these decorators and the `AuthenticatedUser` type from `src/auth/`, but not its services.
- **Meetings:** participants live in `meeting_participants` (composite PK `meeting_id` + `user_id`); the owner is `meetings.owner_id` and isn't added as a participant. Unknown participant ids are rejected with 400 by catching the foreign-key violation (`P2003`) of the single nested `create`, not by looking users up first — meetings never reads the `users` table, and the nested write is atomic, so no meeting is saved. A meeting someone can't see gets the same 404 as a missing one, so ids can't be probed.
- **E2E tests need a migrated DB:** run `pnpm db:up` (root) and `pnpm db:migrate` first. They use the dev DB from `.env`; each test registers a user with a random `@example.com` email.
- **Imports are extensionless** (`import { AppService } from './app.service'`). Never add `.js` — ESLint (`no-restricted-imports`) rejects it. The `@/*` alias maps to `src/*`.
- **Why that works:** this is an ESM package (`"type": "module"`, and Nest 12 itself is ESM-only), which at runtime needs full specifiers. TypeScript uses `moduleResolution: bundler` so it accepts extensionless imports, and the build uses the **SWC builder** (`nest-cli.json`: `builder: "swc"`, `typeCheck: true`), which rewrites them to `./app.service.js` in `dist/`. SWC only does this rewriting when `paths` is set in `tsconfig.json` — do not remove the `paths` entry. Always build/run through `nest build` / `nest start`, not plain `tsc`.
- **Tests use Vitest, not Jest.** Globals (`describe`, `it`, `expect`, `vi`) are enabled; use `vi.fn()` / `vi.spyOn()` for mocks.
- **Linting** comes from `@video-meetings/eslint-config/nest` (typescript-eslint `recommendedTypeChecked`). `no-floating-promises` is an error — await or explicitly `void` every promise. `no-explicit-any` is an error — use `unknown` and narrow it, or write a proper type.
- **TypeScript** config extends `@video-meetings/typescript-config/nestjs.json`: strict mode with `strictPropertyInitialization: false`, decorators and `emitDecoratorMetadata` enabled, `module: esnext` + `moduleResolution: bundler`.
